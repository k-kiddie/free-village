# 6단계 — 사업·공급망·물류·경쟁 (진행 중)

기준 main은 PR #69의 병합 커밋 `d5c6b5316e28ffab65eb7930c6056a707b9355e1`이다. **6단계 전체 완료가 아니다.** 이번 첫 구현은 회사 운영 현황·개인 자금 지원·실제 공급품 발주·운송/귀환·창고 입고와 그 UI/저장 경계를 연결한다.

## 현재 구현

- `/rebuild/api/business`에서 실제 운영 회사의 현금·기업 대출 잔액·지분·회사 지정 고용 계약·건물/설비·사업 분야·동종 회사를 조회한다. 대표의 개인 고용을 모든 회사의 직원으로 중복 계산하지 않는다. 조회는 세계·난수·g/q를 바꾸지 않는다.
- 개인 현금을 회사 현금으로 **지원**하는 공통 명령을 제공한다. 지원금은 자동 지분 발행이나 상환 청구권이 아니며, 확인 화면에 그 조건을 표시한다. 일반 회사의 현재 대표만 실행할 수 있다. 국가 예산이나 금고를 대신 사용하지 않는다.
- 실제 주민이 보유한 판매 가능 재고를 구매한다. 곡식은 본인 기본 비축, 식사는 2개를 남긴다. 구매 대금은 회사→공급자, 운임은 회사→실제 성년 운송인에게 지급하며 기존 소득·세금 계산을 사용한다. 물품 대금과 운임을 미리보기에서 구분한다.
- 운송인은 고용·회사 운영·학업·공무·군무·구금·여행 중이 아니며 건강/영양 조건을 만족해야 한다. 출발 시 native 여행 일정으로 예약해 배송·귀환 기간에 기존 생산 일을 동시에 수행하지 못하게 한다. 화물량은 발주당 최대 20이다.
- 출발 때 공급자 재고→운송 중 화물, 도착 때 화물→회사 창고 재고로 이전한다. 품질도 보존한다. 돈이나 물품을 새로 만들지 않는다. 입고 전 재고를 사용할 수 없다.
- 운송인 사망·구금, 입고 시설 변경/상실은 공급 중단으로 남고 화물을 없애지 않는다. 건강/식량 악화 시 납기와 귀환을 지연한다. 창고는 회사 객체와 별도의 **같은 엔진 S 안의 소유 재고**로 저장해 폐업으로 회사 객체가 사라져도 물품을 버리지 않는다.
- 발주는 기존 계약 등록부에 공급 계약으로 등록한다. 입고 전에는 활성 계약, 입고 후에는 이행된 기록으로 남는다. 운송인 귀환은 별도 상태로 추적한다.
- 사업 화면에서 회사 자금 지원, 품목별 실제 공급자/운송인/도착 비용 비교, 수량 변경·미리보기·발주, 입고/배송 상태를 조작한다. 기존 임금·설비·회사 자금 조달 행동도 해당 회사에서 연다. 회사 이름 변경은 설립 명령과 구분한다.

## 계산과 저장 경계

주민·가족·개인 현금·회사 현금·고용·주식·건물의 기준은 기존 엔진이다. 회사 대금 지급도 `engine.businessPay`를 통해 기존 소득/세금에 기록한다. 새로운 경제나 인구를 함께 실행하지 않는다.

`S.business` v1은 발주 신원, 계약 조건, 실제 운송 중 화물, 실제 회사 창고, 최근 기록을 소유한다. canonical envelope v3의 native S 안에 그대로 저장된다. 기존 v1/v2/v3 저장에 해당 필드가 없어도 읽으며, 조회만으로 새 경제 상태를 만들지 않는다. 미리보기/실패 때 일정·재고·계약·돈을 기존 공통 원자성 경계에서 복구한다.

일일 처리는 기존 `world.step()` 뒤 같은 명령/트랜잭션 안에서 납기·입고·귀환만 정산한다. 생산·임금·소비를 두 번 계산하지 않는다. 자원 회계에는 개인/회사 기존 재고 외에 운송 중 화물과 창고도 포함한다. 저장 응답과 재전송 계약은 기존 Worker 큐를 따른다. main HTTP의 business 조회는 Worker에서 gzip하며 전체 주민 g/q를 내보내지 않는다.

현재 운송은 공급자·운송인 주거와 입고 건물의 **실제 좌표 거리** 및 마을 포장 총량으로 납기·운임을 계산한다. 실제 도로 그래프·구간별 용량·교통 단절을 계산한 것으로 취급하지 않는다. 공급 후보는 회사 가까운 가용 운송인 16명 중 공급자 접근 거리가 짧은 사람과 연결하고 품목별 도착 비용이 낮은 3개 제안을 표시한다. 모든 운송 대안의 전역 최적화를 보장하지 않는다.

## 통과한 검사

- `check-business-supply.js`: 통제한 120명 세계의 회사 조회 불변·대표 권한/회사 잔액·실제 개인→회사 지원·회사→공급자/운송인 지급·재고 보존·운송인 중복 배정 거절·업무 중복 방지·계약 이행·배송/귀환·중단 화물 보존·재전송·도중 JSON 저장 이후 도착일 전체 상태/난수 동일. 같은 물량의 근거리 1일/원거리 5일과 실제 운임 차이 확인.
- `check-business-ui.js`: 통제한 120명 회사/설비/공급 조건에서 실제 모바일 UI로 자금 지원→발주 수량 변경→배송 중 프로세스 재시작→하루 진행→입고→회사 이름 변경을 확인한다. 390×844·844×390 가로 넘침 및 페이지 오류 검사. 일반 무자본 회사 설립 검사를 대체하지 않는다.
- `check-business-scale.js`: 회사 조건을 둔 5,000명 세계의 조회 불변·품목별 후보 제한·응답 100KB 미만·g/q 비전송. 한 실행의 관측은 52ms/1,816B/제안 4개였다. 장기 운영 성능이나 모든 세계의 동일 지연을 보장하지 않는다.
- 기존 `check-common-commands.js`, `check-canonical-session.js`, `check-living-economy.js`, `check-canonical-http.js`, `check-canonical-ui.js` 회귀. HTTP는 기본 512MB Worker·5,000명·저장/세계 전환/복원·ETag·모바일을 확인한다.

## 다음 구현과 완료 조건

1. **생산과 판매 연결:** 입고 재고를 실제 공정·설비·직원·품질·고객에 연결한다. 현재 입고 창고는 보관용이며 기존 사장 개인 생산 재고에 자동 합치지 않는다. 재고 가치의 기업 평가·주주 권리·청산 정산도 이어서 통합한다.
2. **공급 계약과 회복:** 반복 발주, 공급자/운송인 선택과 조건, 기업 간 공급, 중단 화물의 회수·대체 운송·목적지 변경, 폐업 창고의 권리 정산을 구현한다. 현재 중단 화물은 보존되며 자동 복구되지는 않는다.
3. **공간 물류:** 실제 도로·시설 연결/단절·구간별 용량·거리·경로 비용·지연을 세계 지도와 일치시킨다. 현재 직선 거리/마을 포장 수준 계산은 이 완료 기준을 충족하지 않는다.
4. **전략·경쟁·위기:** 저가 대량/고품질 소량/안정 납품 등의 방침을 자동 운영, 고객·직원·공급 의존·경쟁 가격·차입/동업·체불과 연결한다. 기존 경영 버튼과 동종 회사 목록만으로 이 요구가 완료된 것은 아니다.
5. **6단계 완료 검사:** 같은 목표에 지속 가능한 전략 두 개 이상과 실제 비용/위험 차이, 공급 중단의 전파/대응/회복, 지도 변화와 물류 결과, 여러 시드·5,000명·저장/재개·모바일의 연결 플레이를 확인한다.

이후 7~14단계도 남아 있다. 이번 6단계 변경은 별도 초안 PR에서 검토하며 자동으로 병합하지 않는다.
